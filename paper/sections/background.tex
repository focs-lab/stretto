\section{MPI Matching in One Page}
\label{sec:background}

This section covers the parts of MPI the paper needs~\citep{mpi50}. It is meant for
readers who know concurrency but not MPI.

\paragraph{Ranks and messages.} An MPI program runs as $p$ processes, called
\emph{ranks}, numbered $0,\dots,p-1$. Each rank has private memory and executes its own
copy of the program. A send names a destination rank, a \emph{tag} (an integer label) and
a \emph{communicator} (a group of ranks with its own message space). A receive names a
source rank, a tag and a communicator. Either the source or the tag may be a wildcard:
\anysrc or \texttt{MPI\_ANY\_TAG}. A receive $r$ \emph{accepts} a send $s$, written
$r \accepts s$, when they agree on the communicator, $s$ is addressed to $r$'s rank, and
the source and tag of $r$ are either wildcards or equal to those of $s$. When a receive
completes, its \emph{status} reports the actual source, tag and element count. Programs
often branch on this metadata, for example to reply to the sender.

\paragraph{Matching and non-overtaking.} Matching pairs each receive with at most one
send and each send with at most one receive. MPI fixes two ordering rules, and together
they are called \emph{non-overtaking}~\citep[§3.5]{mpi50}. First, if a rank sends two
messages that the same receive accepts, the earlier send matches first. Second, if a
rank posts two receives that both accept a message, the earlier receive takes it. A later
receive cannot be satisfied by a message while an earlier receive that accepts it is
still unmatched. The only freedom left is the arrival order of messages from
\emph{different} senders. A wildcard receive is where that freedom becomes
observable.

\paragraph{Blocking, nonblocking and completion.} \mpicall{Send} and \mpicall{Recv}
block. \mpicall{Isend} and \mpicall{Irecv} return a request at once and complete later,
in a \mpicall{Wait}, a \mpicall{Test} or one of their variants. \mpicall{Waitany}
returns whichever of several requests completes first, a second source of
nondeterminism. A receive is \emph{posted} when it is issued, and matching is decided
then or when a matching message arrives, whichever is later. So a nonblocking receive is
matched long before its wait. \mpicall{Probe} and \mpicall{Iprobe} report the envelope
of a message that a receive would take, without receiving it. Probes with \anysrc drive
polling loops.

\paragraph{Buffering.} A standard-mode send may complete before its receive is posted,
if the library copies the message into a buffer (\emph{eager} protocol). It may also
wait until the receive is posted (\emph{rendezvous}). Implementations choose by message
size: messages up to a threshold go eagerly. Open MPI~4.1 sends up to
\BimplOMPI bytes eagerly on shared memory by default. We model this as a threshold
$\Bt$: a standard send of more than $\Bt$ bytes blocks until matched. Synchronous sends
(\mpicall{Ssend}) always behave as $\Bt=0$, buffered sends (\mpicall{Bsend}) as
$\Bt=\infty$. A ready send (\mpicall{Rsend}) is erroneous unless the receive is already
posted. The same program can deadlock at one threshold and finish at another: two ranks
that both send before they receive deadlock exactly when their messages exceed $\Bt$.

\paragraph{Collectives.} Collective operations (\mpicall{Barrier},
\mpicall{Bcast}, \mpicall{Reduce}, \dots) are called by every rank of a communicator in
the same order. The standard requires no more synchronisation than their data flow needs.
A \mpicall{Bcast} root may return before the others enter, and a \mpicall{Reduce} root
waits for everyone. We model each collective by the synchronisation its \emph{shape}
guarantees.
